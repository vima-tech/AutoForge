> 状态：设计（整合评审稿）+ 实施进行中（见 §9 实施进度）
> 版本：v0.3 · 2026-07-01
> 定位：本文**不新增设计**，只做两件事——① 把三份已存在于独立 worktree/分支的设计文档，
> 按依赖关系拼成一条**可执行的统一路线图**；② 逐阶段标出**影响面（blast radius）与回滚/灰度手段**，
> 让三个较大改动分别以可独立叫停、可独立验收的小步子推进，不出现"改了一半回不去"的中间态。
> 三份源文档已备份于本 worktree（见 §0 路径），保持内容不动，本文只做整合层。

## 1. 总体风险控制原则

三个改动都不小（双头触及 312 个命令、基质要拉新的横切层、孵化台要重写现有生产功能的核心生成逻辑），统一遵循四条原则，贯穿后面所有阶段设计：

1. **能并存，不做大爆炸切换**——旧路径与新路径并存一段时间，新功能默认关闭或走灰度开关，验证稳定后再切默认值、再删旧路径。三份源文档实际上都已经各自设计了并存机制（双头的宏灰度回落、基质的"默认预设=旧函数行为"、孵化台的 P1-P4 分期），本文只是把这条原则显式化、要求全程遵守，不因为赶进度而抄近道跳过灰度期。
2. **能拆小批，不做整块合并**——双头的 312 命令按功能域分批；基质的 14 个 `source_kind` 按价值分批接入；孵化台的 P1-P4 本身就是独立验收批次。每一小批都独立可合并、独立可验收，出问题只影响一批，不影响全局。
3. **每个阶段都有明确的回归验收动作，而不是"看起来没问题就过"**——具体动作见 §3 每个阶段的"验收/回滚"列，能自动化的用 `cargo build`/`cargo test`/`tsc` 自动化，涉及运行时行为的必须过 `npm run tauri:dev` 手动跑一遍功能清单。
4. **高影响面的改动优先安排在低并发/低风险窗口**——凡是改"合并唯一入口""审核门"这类安全铁律相关代码的批次（如双头把 `cr.review_2` 接入 RBAC gate），单独标注、加测试覆盖"无权不能触发 merge"，不与其他批次混跑。

## 2. 为什么必须整合排序（三处关键耦合点）

三者看似正交（基础设施 / 传输层 / 单一功能模块），但存在三处**如果顺序错了就要返工**的耦合点：

### 2.1 孵化台的"上下文账本"是基质的一个局部实例

孵化台设计 §3.4 要给 `blueprint_drafts` 新增 `context_json` 列，手工攒一份"pinned 文件、codegraph 命中缓存、已答问题、工具产出摘要、eval 结论"的账本。

基质设计 §3.2 已经把 `incubator_draft`（blueprint_*）列为 `source_kind` 全集之一，且 §4.2 的 `ContextAssembler` 本就是为了取代"每个子系统各自手搓一份上下文拼装逻辑"而存在的。

**如果孵化台先落地**：`context_json` 会长成一个自成一体、只服务孵化台的 JSON blob；日后基质落地时，要么把它反向适配成 `ContextItem` 投影（多一次改造），要么放任孵化台的账本游离在基质之外（违背基质"取材面覆盖全部过程信息"的初衷）。

**如果基质先落地（哪怕只是 MVP）**：孵化台的账本可以直接用 `context_index` 表登记 + `ContextRequest{include:[incubator_draft, code_agent_log, ...]}` 组装，不用自己管"怎么存、怎么截断、怎么过注入闸"。

**结论：基质（至少 L2 索引表 + L3 最小装配器）应先于孵化台 P1 落地，或至少与 P1 同批设计字段（见 §4 兜底方案，允许并行不互相阻塞）。**

### 2.2 双头的 `Ctx` 契约决定所有新命令怎么写一次

孵化台要新增 `answer_blueprint_question` / `list_prototype_doc_sources`；基质要新增上下文枚举/检索/懒取相关命令。这些命令目前只能按现有 `#[tauri::command] fn(state: State<AppState>, app: AppHandle, ...)` 签名写。

双头 §3.3 已经设计好渐进迁移：新 `#[command]` 宏与旧 `#[tauri::command]` 并存。这意味着**从双头 M1 落地那一刻起，任何新命令都应该直接写成新契约**（`fn(ctx: &Ctx, ...)`），而不是先写旧签名、以后再迁一次。

**结论：不要求基质/孵化台等双头 M0-M3 全部完工，但新增代码从一开始就遵守"事件只走 `event::emit`、命令保持薄包装"（CLAUDE.md 现有铁律），双头 M1 起步时能直接把它们批量套进新契约。**

### 2.3 RBAC 角色 与 基质的"角色收敛台子"是同一个"角色"概念的两种投影

双头 §5.3：`owner/admin/operator/reviewer/viewer`，决定"能做什么"（authz）。
基质 §4.3：产品台/设计台/编码台/测试台/运维台，决定"默认看什么"（Lens）。

两套目前独立设计，语义不同（一个管权限、一个管默认取景框），不能强行合一，但落地顺序错了会埋下"两个 role 概念各说各话"的坑。

**结论：不要求现在合并概念，建议在双头 M5（团队协作角色）落地时，让 RBAC role 作为默认 Lens 的**建议种子值**，其余留给用户自由切换/另存个人预设——这是唯一需要碰头对齐的点，不影响各自现在的设计正确性。**

## 3. 统一路线图：分阶段影响面与回滚设计

> 每一行都是一个**独立可合并、独立可验收**的批次。"影响面"回答"这一批最坏情况能搞坏什么"；"验收/回滚"回答"怎么确认没搞坏、搞坏了怎么退"。

### Track A｜双头 Track 1（核心重构，现在可以立即开工，零业务风险）

| 批次 | 内容 | 影响面（blast radius） | 验收 / 回滚手段 |
|---|---|---|---|
| **M0** | `trait EventSink` + `TauriSink`；约 34 处命令签名 + 约 49 处透传点的 `app: AppHandle` 逐步替换为 `Arc<dyn EventSink>` | 仅事件发射路径；不改业务逻辑、不改数据库 | 替换后行为要求与替换前一致（`TauriSink` 内部仍调 `app.emit` + 通知收件箱副作用不丢）；`cargo build` 强类型检查漏改（签名变了编译不过）；桌面端跑一遍通知收件箱/会议室实时事件收得到即算过 |
| **M1** | `Ctx`/`#[command]` 宏/注册表；`HostCapabilities`；opener 收编；Cargo workspace 拆出 `autoforge-core` | ⚠️**修正**：拆 crate **不是零 touch**——把 `agents/core/tasks/models/db/state` 移入 `autoforge-core`，会强制改写 `commands/`+`lib.rs` 中约 **471 处 `crate::`→`autoforge_core::` 引用（横跨 42 文件）**。命令**逻辑**不变，但文件被动。**必须用 re-export 垫片压 churn**：在 `lib.rs` 加约 6 行 `pub use autoforge_core::{agents,core,tasks,models,db,state};`，`crate::agents::` 即仍可解析，改动才真正压到近零 | 验收 = ① 加垫片后 `git diff --stat` 确认命令文件未被大面积改写 ② 至少 1 个只读命令走注册表功能等价 ③ `cargo tree -p autoforge-core \| grep tauri` 为空。回退 = 垫片方案本身可整体 revert，不留半迁移态 |
| **M2** | 分批把约 313 个命令迁到统一契约，**按功能域分批**（如先迁 `projects.rs`，再迁 `issues.rs`……） | 每批仅限该功能域；未迁移命令仍在旧路径可用 | 灰度回落是天然的回滚开关——某批出问题，把该批命令从注册表摘除即回落旧路径，不影响已迁移的其他批次；每批合并前必须过一遍 `npm run tauri:dev` 覆盖该功能域的手动回归清单 |
| **M3** | Tauri 对接层瘦身为单 dispatch，清空 `generate_handler!` 长清单；验收**对接层不得枚举命令名**（双头 §2 红线：出现 `match cmd{...}` 或命令清单即不合格） | 全部命令的注册入口收敛为一处；这是本 Track 唯一"一旦切换不能局部回退"的批次 | 切换前用脚本断言"旧 `generate_handler!` 清单里的每一条都已出现在新 registry"（避免遗漏没注册进去导致某功能突然 404）；切换当天预留完整回归窗口，不与 M2 混批 |

**M0-M2 可以立即、独立、逐批开工，不依赖基质或孵化台是否启动。M3 建议放在 M2 全部批次跑完之后再做，作为 Track A 的收尾动作。**

### Track B｜基质 MVP（建议紧随双头 M1 之后，或与孵化台 P1 并行·见 §4 兜底）

| 批次 | 内容 | 影响面 | 验收 / 回滚手段 |
|---|---|---|---|
| **B0** | 新增 `context_index` 表（登记索引，不搬正文） | 纯新表，不改任何现有表结构 | 零风险，`cargo test` 通过即可，不需要额外回滚设计 |
| **B1** | `ContextAssembler` 包一层 `load_project_context_for_conversation`（现址 `commands/project_context.rs:340`，仅 2 处调用点） | 影响会议室上下文装配——AutoForge 最核心的路径之一，回归代价高 | **黄金测试先行**：对固定样本项目跑"旧函数输出 vs 新 Assembler 默认预设输出"做 diff，要求**结构级一致 + 固定样本零差异**才允许切换调用点（因函数 async 读实时 DB/文件，字节级复现需固定 fixture，不苛求线上字节级）；切换后保留旧函数体一段时间，调用处一行开关可紧急回退 |
| **B2** | 渐进接入高价值 `source_kind`：`material` / `code_agent_log` / `llm_trace` / `incubator_draft` | 每接一个 source_kind 是独立小改动，互不影响，可任意顺序、任意暂停 | 逐个验收"该来源能被检索到 + 正文能懒取 + 体积预算生效"；某个来源出问题只需要撤回它的适配器，不影响已接入的其他来源 |
| **B3（可选，晚做）** | 接入 `mcp_result` / `web_result` 等 `external_untrusted` 来源 | 涉及注入闸，安全敏感 | 必须先过 `has_obvious_injection` 单测覆盖，再接入；不与 B2 混批 |

### Track C｜孵化台深化 P1-P4（源文档已有的四期，本文只补充影响面标注）

| 批次 | 内容 | 影响面 | 验收 / 回滚手段 |
|---|---|---|---|
| **P1** | `spec_writer` 接工具循环 + codegraph + 上下文账本 | **改变现有生产功能的核心生成逻辑**（从"强制单轮 JSON"变成"多轮工具循环"）——正在用孵化台的用户体感会直接变化，是本文标注的**全局最高风险单点** | 建议加一个显式开关（如 `blueprint_draft_mode: legacy \| tool_loop`），先让工具循环模式在小范围/新项目验证"能稳定收敛出结构化 JSON"，观察若干轮后再切默认；`update_draft` 工具产出仍需符合原有 `{prd_markdown, specs, tasklist}` 契约，保证下游（编码工单消费方）零改动 |

**P1 是全路线图里唯一"改变现有功能默认行为"的批次，建议单独窗口推进、开关驱动灰度，不与其他任何批次混跑。P2-P4 风险递减，可以正常节奏推进。**

## 4. 兜底方案：如果不想等基质 MVP，孵化台 P1 现在就要并行推进

用户可能出于节奏考虑，选择孵化台 P1 与基质 B0-B1 **并行**开工（而非严格等基质先合并）。为了不让 §2.1 的返工发生，给孵化台 P1 一个**兼容性写法**：

`blueprint_drafts.context_json` 内部结构直接采用与基质 §3.1 `ContextItem` 同构的数组：

```json
{
  "items": [
    { "source_kind": "codegraph_hit", "title": "...", "content_ref": "...", "created_at": "...", "labels": [] },
    { "source_kind": "answered_question", "title": "...", "content_ref": "...", "created_at": "..." }
  ]
}
```

而不是随意设计一个孵化台专属 schema。这样即使基质 MVP 晚于孵化台落地，日后要把 `context_json` 数组收编进 `context_index` 表，只是"批量 INSERT 一遍已有 JSON 数组"的数据迁移，不需要改写字段语义或调用方代码——**孵化台不必等基质，但要向基质的形状看齐**。

同理，孵化台新增的 `AppEvent::BlueprintThinking` 事件、`answer_blueprint_question` 等命令，只要遵守"事件走 `event::emit`、命令签名不裸传 `AppHandle` 到深层业务函数"这两条铁律，双头 M1 落地后可以直接套进新契约，不需要特殊改造。

## 6. 与 CLAUDE.md 现有铁律的一致性检查

三份源文档各自都做过这项自检，这里只确认**没有相互冲突**，并补充一处需要联调的安全点：

- ✅ 三者都坚持"业务逻辑不依赖 Tauri 类型、事件只走 `event::emit`"——双头把这条铁律升级为编译期强制，基质与孵化台的新代码天然遵守，无需额外改造。
- ✅ 三者都坚持"迁移文件只增不改"——基质的 `context_index`、孵化台的 `context_json`/`eval_json`/`pending_question`、双头的 `0081_users_auth.sql` 是三个独立的新迁移文件，序号按落地顺序取号（谁先合并谁先占号）。
- ✅ 三者都坚持外部/不可信内容必过 `has_obvious_injection`——基质把这条泛化为 `trust` 字段贯穿全基质，语义一致。
- ⚠️ **需要联调的安全点**：双头引入 `Principal`/RBAC 后，基质 `ContextItem` 目前没有"谁能看这条 Context Item"的可见性字段。双头 M5（团队 ACL，`scope(ctx)`）落地时，基质的检索/懒取也必须经过同一个 `scope(ctx)` 过滤，否则会出现"项目级 ACL 挡住了业务命令，但基质的上下文检索绕过 ACL 直接读到别人项目的 Context Item"的越权缺口。**这一点只在 Track B 与 Track D-M5 都落地后才会真正出现，本文提前标出，届时必须联调补上，不能各自验收各自的就算完。**

## 8. 小结

- 三份设计彼此不冲突，可以都做，核心是**排序 + 影响面隔离**：Track A（双头核心重构）现在就能独立、分批、零风险地开工；Track B（基质 MVP）建议紧随其后或与 Track C 并行（用 §4 兜底方案解耦依赖）；Track C（孵化台）的 P1 是全路线图唯一改变现有功能默认行为的批次，需要开关灰度、单独窗口，P2-P4 风险递减可正常推进；Track D（双头团队协作）按 Gate 条件启动。
- 每个批次都设计了独立的验收/回滚手段（§3 表格），不存在"改了一半退不回去"的中间态。
- 唯一一处需要在两条 Track 都落地后专门联调、而不是现在就要设计到位的安全点：**双头的项目级 ACL（M5）与基质的上下文检索必须共用同一个 `scope(ctx)` 过滤**（§6 ⚠️）。
- 本文不改变三份源文档任何一条设计结论，只提供排序、契约对齐与风险控制建议；§5 的 6 个取舍点仍需用户逐条裁定。
