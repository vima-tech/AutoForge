> **状态：已实现（Phase 0–2 全部落地）。** 迁移 `0070_change_request_issues.sql`；后端
> `commands/requirement_merge.rs`（探测，含 6 个单测）+ `change_requests.rs`（`review_1_merge` /
> `split_change_request` / `get_change_request_issues` + 全组联动助手 `cr_issue_ids` /
> `set_cr_issues_status`）；执行层多需求工单（`code_agent::build_prompt` 新增 `merged_requirements` +
> `render_merged_requirement`）；全组状态联动覆盖 execution / merge 流水线 / review_2 / 解冲突 /
> revert / restore / retry / 启动恢复；前端 `Audit.tsx` 候选 chip + 批量菜单合并入口 + `MergeConfirm`
> 面板 + CR 头部「覆盖 N 个需求」。`cargo test` 175 通过、clippy 干净、`npm run build` 通过。
>
> 目标：当多个需求（issue）经分析后命中**重叠的目标文件**时，把它们合并成**一次编码执行**（一个 worktree、一个 diff、一条审核），而不是各自起一个 CR 反复改同一个文件——后者会产生合并冲突、重复加载上下文、浪费算力。

## 1. 现状与约束（已核对代码）

链路：`issue` 提交 → 分析任务产出 `issue_analyses.analysis_json`（含 `scope.affected_files[].path`、`claude_code_brief.files_to_touch`）→ 需求审核 `review_1` 通过 → **1 个 issue 创建 1 个 CR**（`approve_issue_review_1`，`change_requests.rs:498`）→ 入队 Execution → worktree 编码 → 代码审核 `review_2` → 合并。

关键耦合点（合并改造必须照顾）：

- `change_requests.issue_id` 是**单值**，全仓约 19 处引用（`merge.rs`/`conflicts.rs`/`change_requests.rs`）。
- `execution.rs:60` 用 `cr.issue_id` 加载唯一 issue，`build_prompt`（`execution.rs:270`）从单条 issue 的 title/description + 分析 spec 拼工单。
- `merge.rs` 的 `set_status(db, cr_id, &cr.issue_id, status)`（贯穿全文）用 `cr.issue_id` **同步更新 issue 状态**——CR 状态机和 issue 状态机靠这一个字段联动。
- 已有批量需求审核 `review_1_batch`（`change_requests.rs:606`）+ 前端 `review1Batch`，Audit 页已有多选批量通过的 UI 面，合并入口可复用这块。
- 分析阶段已检测 `duplicate_of`/`is_duplicate`（同一需求重复），但**没有**"不同需求命中同一文件"的聚类——这是本功能要补的缺口。

## 2. 核心设计决策

### 2.1 数据模型：`issue_id` 保留为「主需求」+ 新增成员关联表

不改 `change_requests.issue_id` 的语义（继续作为 CR 的**主需求**，驱动默认标题/Innate 召回/旧调用点），**新增一张关联表**承载「合并进来的成员需求」：

```sql
-- src-tauri/migrations/0070_change_request_issues.sql
CREATE TABLE change_request_issues (
  change_request_id TEXT NOT NULL,
  issue_id          TEXT NOT NULL,
  role              TEXT NOT NULL DEFAULT 'member',  -- 'primary' | 'member'
  sort_order        INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (change_request_id, issue_id)
);
CREATE INDEX idx_cri_cr    ON change_request_issues(change_request_id);
CREATE INDEX idx_cri_issue ON change_request_issues(issue_id);

-- 回填：每个既有 CR 写一条 primary 行，保证「CR 的全部需求」= 关联表查询，新旧一致
INSERT INTO change_request_issues (change_request_id, issue_id, role, sort_order)
SELECT id, issue_id, 'primary', 0 FROM change_requests;
```

**为什么这样最可落地**：旧的 19 处 `cr.issue_id` 读取**全部保持工作**（操作主需求），只把「必须考虑全部需求」的少数地方升级为查关联表。避免一次性重写整条状态机。

### 2.2 合并触发：人工闸门（推荐）

符合 AutoForge「双审核节点 / Human-Lite」哲学：系统**自动探测**候选合并组，在**需求审核闸**把候选呈现给操作者，**人工点头**才合并。不做 AI 静默捆绑（避免把无关需求强行打包）。

- 候选探测纯规则、零 LLM 成本，随需求审核队列实时算。
- 可选 Phase 3：加一个「合并顾问」Agent 预判兼容性 + 生成合并工单，但**仍由人确认**。

### 2.3 合并条件（候选探测规则）

两个/多个 issue 进入同一候选组的条件：

1. 同 `project_id`；
2. 均处于 `pending_issue_review`（已完成分析，有 `analysis_json`）；
3. **共享实质文件**：各 issue 的 `scope.affected_files[].path ∪ claude_code_brief.files_to_touch`，全体成员共享 ≥ 1 个**实质文件**（"针对单个文件的多个需求"的核心触发，"实质"定义见 2.4）；
4. 安全护栏：组内需求数 ≤ 上限（默认 5）；合并后总 `affected_files` 去重数 ≤ 上限（默认 ~15，防止滚雪球）；
5. 冲突预过滤（弱）：若 A 的 `constraints.must_not` 与 B 的 `expected_behavior`/`must` 在同一文件上明显矛盾，则**标红提示但不阻止**，交人工判断。

### 2.4 部分重叠与枢纽文件（关键）

**不拒绝部分重叠**——纯子集/完全相同的文件集罕见，部分重叠才是常态与主要价值；合并要规避的冲突只要有 1 个共享文件即成立，与私有文件无关。改用**分级**而非二元：

| 档位 | 条件 | 处理 |
|------|------|------|
| 强候选（自动建议） | 全体成员共享 ≥1 实质文件，且合并后去重 `affected_files` ≤ 上限 | 队列高亮，一键合并 |
| 弱候选（展示但弱化） | 仅共享登记类文件，或重叠占比低 | 列出并标注「仅共享 lib.rs 这类登记文件，合并收益小」，默认不勾 |
| 不建议 | 无共享实质文件 / 超 blast radius 上限 / 检出冲突 | 不进候选 |

重叠强度量化：`overlap = |A∩B| / min(|A|,|B|)`（相对小集合，对小需求并入大需求更友好）；blast radius 用合并后去重总文件数封顶。

两个必须处理的陷阱：

- **枢纽文件（hub）虚假大簇**：`lib.rs`(invoke_handler) / `services/index.ts`(IPC) / `mod.rs` / 迁移目录 / `*.md` 等几乎每个需求都命中。探测时**降权高频文件**：统计某文件在当前队列被多少 issue 命中，命中过广（占队列比超阈值，或在内置登记集内）的不计入「实质重叠」。
- **传递性串联**：A∩B、B∩C 非空但 A∩C 空，连通分量会经 B 把 A、C 强行拉一起。用**团（clique）语义**——一个合并组要求**全体成员共享同一实质文件**，而非两两链式。

部分重叠合并后，私有文件在同一 pass 顺带做掉（上下文已加载，近零额外成本，净收益为正），前提是工单**逐需求标清各自 files_to_touch**（Phase 1 多需求工单已覆盖），避免 agent 改动外溢。

- [ ] **合并命令** `review_1_merge(issue_ids, suggestions, admin_id)`（`change_requests.rs`）：
  - 校验全部为 `pending_issue_review` 且同项目；
  - 创建**一个** CR（primary = 优先级最高/最早的那条），写 1 primary + N member 关联行；
  - 全部 issue 翻 `pending_execution`；逐条 `record_admin_decision(stage=review_1, approved)`；
  - 入队**一个** Execution job（idem `execution:{cr_id}`）。

- [ ] **候选探测命令** `list_merge_candidates(project_id) -> Vec<MergeCandidate>`：解析队列内各 issue 的 `analysis_json`，按文件交集聚类，返回 `{ issue_ids, shared_files, conflict_hint }`。
- [ ] **执行合并工单** `execution.rs`：
  - 若 CR 有 member（关联表 > 1 行），加载全部 issue + 各自分析 spec；
  - `build_prompt` 增加多需求路径：拼成「本次变更合并实现以下 N 个需求，请一次性完成全部并逐条满足验收标准」+ 每条的 objective / acceptance_criteria / files_to_touch；
  - 合并去重后的 `affected_files` 喂 `code_intel::locate_context`；
  - Innate 召回 query 用主需求文本（或拼接，二选一，先用主需求）。
- [ ] **状态机联动** `merge.rs`：`set_status` 改为更新 CR 的**全部成员 issue**（查关联表），而非单 `cr.issue_id`；review_2 拒绝/回滚同理全组联动。`conflicts.rs` 加载 issue 处按需取全部成员（展示用主需求即可）。
- [ ] **review_2 决策记录** 对全部成员 issue 各记一条 admin_decision。
- [ ] **拆分兜底**（可选但建议）`split_change_request(cr_id, issue_id)`：把某成员需求从 CR 移除、退回 `pending_issue_review`，应对「合并后想撤回其中一条」。

### Phase 2 — 前端（Audit 需求审核区）

> 复用现有「多选 `LedgerCheck` + 底部批量操作条 + mention-pop 下拉 + ConfirmModal」骨架。
> 注意区分：今天的**批量通过**（`review1Batch`）给每条需求各建一个独立 CR（1:1，会在共享文件上撞车）；本功能的**合并**是 N 条 → 1 个 CR、一次 worktree、一条审核。二者并存，是不同动作。

交互流程（两个入口）：

- **入口 A · 系统建议**：探测器发现候选组时，相关行挂 `<Icon name="merge">` chip，如「可合并 · 共享 `src/foo.rs`」；点 chip 选中整组并打开合并面板。"自动探测 + 人工点头"主路径。
- **入口 B · 手动合并**：操作者用现有勾选框选 ≥2 条 → 底部「批量操作」下拉新增项「合并为一次变更…」→ 对当前选区打开合并面板（探测器没建议也允许人工强合）。

合并确认面板（模态，遵守 DESIGN：`inset:var(--win-gutter)`、不点遮罩关闭、仅 ✕/Esc、每屏 ≤1 个 `.btn-primary`）：
- 标题「合并 N 个需求为一次变更」；
- **共享文件**区高亮 + 每条需求的私有文件弱化灰显（直观呈现部分重叠）；
- **主需求**选择器（`proj-select`，默认优先级最高，决定 CR 标题/Innate 召回）；
- 合并后**去重总文件数**计数，逼近上限标红；有 `must_not` 冲突的需求挂红 badge；
- 共享补充意见输入（`admin_suggestions_1`）；
- 主操作「合并并进入编码」→ 调 `review1Merge(issueIds, primaryId, suggestions)`。

## 4. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 合并后 review_2 被拒，整组需求一起退回 | 组内需求数/总文件数设上限；提供 `split_change_request` 拆回；冲突预过滤标红 |
| 主需求假设（一个 issue 一个在途 CR）被打破 | 成员 issue 合并时离开 `pending_issue_review`，不能被二次单独通过；`review_1_merge` 内事务校验状态 |
| 旧调用点只看 `cr.issue_id` 漏掉成员 | 仅状态联动/审核记录/工单这几处升级查关联表；展示类继续用主需求无害 |
| 启动恢复/幂等 | Execution idem 仍按 CR 唯一，天然安全；合并是 CR 创建期的一次性动作 |
| Innate 召回只用主需求文本 | Phase 1 接受；如效果差再改拼接 |

## 5. 落地顺序建议

Phase 0 → Phase 1（后端闭环，可单独验收：手工造两个同文件需求 → 合并命令 → 一次 worktree 出双需求 diff → review_2 全组联动）→ Phase 2（UI）→ Phase 3（AI 顾问，按需）。
