# 脏输入压测 Dogfooding 方案

> 定位:这不是"测试工厂能不能跑",而是**故意把工厂往真实外包场景里摔,记录每个崩点,产出一张排好序的崩点清单 = 阶段二待办**。
> 背景:AutoForge 现阶段自用提效,阶段二面向小型软件外包公司售卖。外包公司**自带过载上游**,真正的风险不是"没需求",而是工厂能否在脏输入 + 存量仓库上稳定转化。

---

## 0. 实验定位

一句话:**这不是测试,是证伪。** 把每条"理所当然"的假设变成一个"我赌它会崩"的命题,用脏输入去撞。崩了就记账,**先记账、后修**——边撞边修会看不清崩点的分布规律。

⚠️ 陷阱预警:别让"做实验"变成逃避客户访谈的新借口。**dogfooding 与找外包公司访谈是并行两条线,不是先后。** 实验给产品答案,访谈给需求答案,缺一不可。

---

## 1. 选什么项目(入料容器)

**硬标准:**
- ✅ **存量/遗留**,不是 greenfield——有历史包袱、风格不统一、测试覆盖烂
- ✅ **不是 AutoForge 自己**——太干净、太熟、还自指,三重污染
- ✅ **小到能一眼看懂 diff 对不对**(否则 review 2 没法判),但真到能给惊喜

**推荐选 2 个,控制变量:**

| 项目 | 作用 | 隔离的变量 |
|------|------|-----------|
| A:自己一个陈年烂尾 side project(同栈) | 隔离"脏输入"单一变量 | 栈熟 → 崩点一定来自输入/流程 |
| B:陌生技术栈的小型真实仓库(朋友小生意 app / issue 很乱的小 OSS) | 测"栈无关性" | 外包=多栈,阶段二硬假设 |

先跑 A 把流程跑顺,再上 B 看换栈是否整套塌掉。

---

## 2. 喂什么(脏需求样本)

别写干净 issue,写甲方真会发的垃圾。**走"对话"入口喂**(不走规整表单,才测得到"炼噪声为需求"那段)。8 个原型 + 可直接粘贴样例:

1. **一句话模糊**:"登录有时候进不去,修一下"
2. **无复现的截图式 bug**:"昨天那个页面报错了"(无截图/路径/步骤)
3. **超范围塞一起**:"加个用户系统,顺便首页也改好看点,下周一要"
4. **隐含上下文**:"按上次说的那样改"(工厂没有"上次")
5. **一条其实是两条**:"导出功能加一下,还有那个慢的问题也看看"
6. **不可执行的感受**:"整体感觉有点卡 / 不够高级"
7. **抄竞品**:"做成像 XX 那样"(无细节)
8. **自相矛盾/会变卦**:先"要弹窗确认",过会儿"算了别弹了"

每项目喂 6-8 条,共 **12-15 条**,够看出崩点分布。

---

## 3. 观测哪几个崩点(按流水线分阶段)

每阶段一个核心命题 + 通过/失败判据:

**① 入料 / 炼噪声为需求**
- 命题:`has_obvious_injection` 误杀正常人话,或漏放。
- 命题:分析 Agent 面对模糊输入是**追问澄清**还是**默默猜范围**?
- 🔴 外包致命点:**静默猜错 = 烧客户的钱**。从不追问、总自信编范围 → 阶段二头号红线。

**② 分析 / 审核 1**
- 判据:分析产出是否**让你 2 分钟内能 yes/no**?还是没法点头的糊状物?
- 真实输入下去重/严重度/分类还成立吗?

**③ 在存量仓库上执行(最大未知)**
- worktree 在有 submodule / 怪结构 / 巨大 node_modules 的仓库上能建吗?
- claude CLI 顺着既有风格写,还是自顾自一套跟原仓库打架?
- 尊重既有测试吗?会补测试吗?
- 🔴 **`.autoforge/specs` 假设**:新客户仓库没有这目录。优雅降级还是直接崩?这是 greenfield→存量 的核心断层。
- 禁用 git 工具后会卡死吗?会动 scope 外文件吗?

**④ 正确性 / 审核 2**
- 判据:你**真敢信**这个 diff 吗?
- 📊 **计时**:每个 CR 的 review 2 几分钟?——阶段二成本模型,必须量化。
- 合并前自动测试,在**没有测试框架**的客户仓库里无测可跑——拦截机制失效会发生吗?

**⑤ 合并**
- 真实仓库 merge to dev:冲突?自指合并坑已踩过;客户仓库你不控制 main。

---

## 4. 记账本(每条需求记一行)

做成表,逐行填。**用现有 Trace 页面(`llm_traces`)回看每步怎么推错的**——有现成可观测性,别浪费。

| 字段 | 记什么 |
|------|--------|
| 输入原文 / 原型# | 哪种脏 |
| 入料是否炼成需求 | Y/N + 备注 |
| 是否需要澄清 | **追问了 / 静默猜了(危险)** |
| 到审核1耗时 | 分钟 |
| 执行成功 | Y/N |
| diff 质量 | 1-5 主观分 |
| **review2 人工耗时** | 分钟 ← 成本模型 |
| 是否合并 | Y/N |
| 返工轮数 | 0/1/2+ |

> 本记账本将固化为系统内的一种 **dogfooding trace 模板**,使每条脏输入沿流水线的逐阶段结局可结构化记录、可定位崩点。详见配套实现。

---

## 5. 唯一的北极星指标

> **脏输入中,有多大比例能在「≤1 轮人工澄清」内走到「可合并且正确的 PR」,以及每个交付 CR 花掉多少人工分钟。**

这就是销售话术(或现实暴击)。80% / 5 分钟 → 你有产品;20% / 40 分钟 → 你卖的是"AI 辅助"不是"工厂",定位得改。

---

## 6. 停止条件与产出

跑完 12-15 条 × 1-2 仓库,把记账本里所有"崩"的行按 **(频次 × 阶段致命度)** 排序——**这张排序表 = 阶段二 roadmap**,用真实数据而非直觉排出。先别修,跑完再看模式。
