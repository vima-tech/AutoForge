## 1. 后端独立化（EventSink 抽象） — P0

### 1.1 现状缝隙（已核对 CLAUDE.md「后端独立化愿景」+ 代码）

耦合"浅但宽"，唯一的"宽"耦合是 `AppHandle` 被当事件 sink，一路透传进
`tasks/runner.rs → tasks/{analysis,execution,merge}.rs → commands/orchestration.rs` 几乎每个函数签名，**只为调 `event::emit`**。其余核心（`agents/llm.rs`、`db.rs`、`core/concurrency.rs`、`core/git.rs`、`state.rs::AppState`）已是纯 Rust。

> 这是把后端拆成可独立运行服务的**最后一道宽缝**。补上后，未来上 Web/远程/CI 接入只需换传输层，业务零改。

### 1.2 设计决策：用 `trait EventSink` 替换裸 `AppHandle` 透传

不立刻拆服务（成本高、收益延迟），而是**先做一次"无行为变更"的抽象重构**，把"事件出口"从具体的 `AppHandle` 抽象成 trait。这样：
- 当前仍用 Tauri 实现，运行行为 100% 不变（零回归）；
- 未来换 HTTP/WebSocket/CLI 入口时，只实现一个新的 `EventSink`，业务签名不动。

```rust
// src-tauri/src/core/event.rs  —— 新增
pub trait EventSink: Send + Sync + 'static {
    fn emit(&self, event: AppEvent);
}

// Tauri 实现（薄）：包住 AppHandle
pub struct TauriSink(pub tauri::AppHandle);
impl EventSink for TauriSink {
    fn emit(&self, event: AppEvent) {
        let _ = self.0.emit("autoforge://event", &event); // 唯一一处 app.emit
    }
}
```

### 1.3 改动点（机械替换，量大但风险低）

1. `core/event.rs`：新增 `trait EventSink` + `TauriSink` + 现有 `emit()` 改为 `sink.emit(event)`。
2. 全仓把函数签名里的 `app: &AppHandle`（仅用于 emit 的）替换为 `sink: &Arc<dyn EventSink>`。涉及：
   - `tasks/runner.rs`（任务池主循环，持有 sink 并下传）
   - `tasks/analysis.rs` / `tasks/execution.rs` / `tasks/merge.rs`
   - `commands/orchestration.rs`（`execute_conversation_task` 及其下游）
   - 持久化通知适配层（记忆「操作者身份卡+通知收件箱」记录：持久化已挂在 `event::emit` 适配层，零改 44 处调用点 → 本次同样受益，只需适配 sink）
3. `state.rs::AppState` 增持 `event_sink: Arc<dyn EventSink>`（在 `lib.rs` setup 时注入 `TauriSink`），业务从 state 取 sink，而非从命令参数透传 `AppHandle`。
4. `#[tauri::command]` 保持薄包装：命令体内取 `state.event_sink.clone()` 传入纯 async fn。

### 1.4 分阶段

- **Phase A**：落 `trait EventSink` + `TauriSink`，`AppState` 增字段，`event::emit` 改签名。编译通过、运行行为不变。
- **Phase B**：逐文件把 `AppHandle` 参数换成 `Arc<dyn EventSink>`（runner → tasks → orchestration），每换一个文件单独编译+冒烟。
- **Phase C（可选，远期）**：新增非 Tauri 入口（如 `bin/autoforged.rs` 起 axum HTTP + WS sink），验证后端可脱壳运行。Phase C 不在本期，但 A/B 完成后即"可拆"。

### 1.5 工作量 / 风险

- A+B 约 1–2 天，纯机械替换 + 编译驱动；**无新功能、无 schema 变更**，回归风险极低（行为等价）。
- 风险点：`orchestration.rs` 里若有除 emit 外其他 `AppHandle` 用途（如 `Manager` 取 state），需保留或改从纯依赖传入——重构时逐个甄别，凡非 emit 用途均按铁律改参数传纯依赖。

## 2. 成本与用量治理看板 — P0

### 2.1 现状缝隙

记忆「LLM 链路追踪」：已有 `llm_traces` 表 + `core/trace.rs`（task_local），**记录了所有 LLM/工具/MCP 出入参**，且独立 Trace 页面已存在。但目前是**逐条 trace 浏览**，没有：token/费用聚合、按项目/角色/时间维度的用量看板、预算闸口与超额告警。数据已在库里，缺的是聚合视图 + 闸口。

### 2.2 设计决策：复用 llm_traces，加"聚合 + 预算"两层，不新采集

- **聚合层**：在 trace 落库时确保记录 `prompt_tokens` / `completion_tokens` / `model` / `forge_role` / `project_id`（缺哪个补哪个，迁移加列），费用按 `llm_configs` 维护的单价表算（新增单价字段），DB 侧聚合查询。
- **预算层**：`app_settings` 加项目级/全局月度预算；任务入队前/LLM 调用前软校验，超额走 `AppEvent::BudgetExceeded` 告警（复用通知通道）+ 可配置"软提醒/硬阻断"。

### 2.3 数据模型 / 迁移

```sql
-- 0071_llm_cost.sql
ALTER TABLE llm_traces ADD COLUMN prompt_tokens  INTEGER;     -- 若已有则跳过
ALTER TABLE llm_traces ADD COLUMN completion_tokens INTEGER;
ALTER TABLE llm_configs ADD COLUMN price_input_per_1k  REAL;  -- 单价（可空=未知）
ALTER TABLE llm_configs ADD COLUMN price_output_per_1k REAL;
-- 预算存 app_settings（key/value），无需新表：
--   budget.global.monthly_usd / budget.project.<id>.monthly_usd / budget.mode (warn|block)
```

### 2.4 改动点

- 后端：`agents/llm.rs` 落 trace 时补 token 字段（多数 provider 响应已带 usage，解析即可）。新增 `commands/cost.rs`：`get_cost_summary(project_id?, from, to)`（按角色/模型/天聚合）、`get_budget` / `set_budget`。`mod.rs` + `lib.rs` 注册，`services/index.ts` 封装。
- 预算闸口：任务入队点（`tasks/runner.rs`）/ LLM 调用前读 `app_settings` 预算，超额 emit `AppEvent::BudgetExceeded`（加进 enum），mode=block 时拒绝入队并标注原因。
- 前端：Trace 页面（或 Settings）加「用量」tab —— KPI 卡（本月 token/费用、按角色 Top）+ 趋势（复用 `.stat`/`.panel`，禁硬编码色，趋势用语义色）。预算设置走 `.field` + `.switch`。

### 2.5 工作量 / 风险

- 约 2–3 天。风险低：读多写少，预算默认关闭（warn 模式不阻断），不影响现有流水线。
- 注意：单价表可能不全/过时 → 费用展示标"估算"，单价留空时只显 token 不显费用。

## 3. MCP 写类工具白名单 — P1

### 3.1 现状缝隙

记忆「后端独立化+MCP」+ CLAUDE.md：MVP 阶段**只允许只读/无副作用工具，写类工具默认禁用**。MCP 工具结果视为不可信外部输入，回灌前过 `has_obvious_injection()`。要解锁"平台"能力（让 Agent 调用外部写类工具，如建 issue、发 PR 评论、写 Jira），需要一套**可控的写工具放行机制**，而不是简单去掉禁用开关。

### 3.2 设计决策：三闸放行（白名单 + 副作用声明 + 人工确认档）

不做"全局开关一刀切"。每个 MCP 工具按以下分级：

| 档 | 条件 | 行为 |
|----|------|------|
| 只读（现状） | 工具 schema 无副作用标记 | 自动可用 |
| 写-自动 | 在白名单 + 标记幂等/低危 | 自动执行，全程记 trace |
| 写-需确认 | 白名单 + 高危（删除/发布/外发） | 暂停任务，走人工确认闸（复用通知收件箱），点头才执行 |
| 禁用 | 不在白名单 | 拒绝，记审计 |

### 3.3 数据模型 / 迁移

```sql
-- 0072_mcp_tool_policy.sql
ALTER TABLE mcp_servers ADD COLUMN write_policy_json TEXT;  -- 每工具：{tool_name: {mode: ro|auto|confirm|deny, reason}}
-- 默认全 deny（向后兼容：旧 server 无此列 = 维持只读）
```

### 3.4 改动点

- `agents/tools/mcp.rs`：调用前查 `write_policy_json` 判档；`confirm` 档 emit `AppEvent::McpWriteConfirmRequested`（入 enum），阻塞等待人工决策（复用 conversation_tasks 暂停/恢复机制或新增轻量等待态）。
- 所有写工具结果仍过 `has_obvious_injection()`；写工具调用**强制记 trace**（含参数全文），便于审计与回溯。
- 前端：Settings 的 MCP 服务器编辑页加「工具策略」子面板（每工具下拉选档，禁原生 select，用 proj-select）。
- **铁律**：MCP client 不得引用 Tauri 类型，确认事件走 `event::emit`。

### 3.5 工作量 / 风险

- 约 3–4 天。风险中：写工具有真实副作用 → 必须默认 deny、确认档默认开、全审计。先在内部低危工具（如 code-intel 之外的只读增强）灰度，再开放写。

## 4. 自动测试生成 + 验收门 — P1

### 4.1 现状缝隙

记忆「合并并行化」「Schema 驱动 Agent」：合并前已有 `run_and_gate`（测试门）+ `Testing` schema，但**测试靠项目自带命令**（`run-config.json` 的 test 命令）。缺：① 当 CR 改动缺乏对应测试时，自动让 Agent 补测试；② 把"验收标准"做成结构化、可校验的闸口（而非仅"测试命令退出码=0"）。

### 4.2 设计决策：验收标准入分析阶段 + 执行后测试缺口检测 + 可选补测

- **验收标准结构化**：分析阶段（`agents/analysis.rs`）的 schema 输出已含 `expected_behavior`；扩展为结构化 `acceptance_criteria[]`（每条：描述 + 可校验方式 hint）。审核闸（review_1）人工可编辑。
- **测试缺口检测**：执行后、合并前，用代码情报/diff 判断"改了 X 但无 X 的测试"。命中则按风险决定：High 风险 → 自动追加一轮"补测试"编码任务；Low → 仅告警。
- **验收门**：review_2 通过 → run_and_gate 跑项目测试 + 校验 acceptance_criteria（能自动校验的自动跑，不能的列给人审勾选）。失败阻断合并（符合 testing.md 规范）。

### 4.3 数据模型 / 迁移

```sql
-- 0073_acceptance.sql
ALTER TABLE issue_analyses ADD COLUMN acceptance_json TEXT;   -- [{id, desc, check_hint, auto_checkable}]
ALTER TABLE change_requests ADD COLUMN acceptance_result_json TEXT; -- 每条通过/失败/待人工
```

### 4.4 改动点

- `agents/analysis.rs`：schema 增 `acceptance_criteria`（沿用 schema.rs 版本化机制，记忆「Schema 驱动」）。
- `tasks/execution.rs`：执行后调测试缺口检测（复用 `agents/tools/code_intel.rs` 的影响面）；High 风险且缺测 → 追加补测试子任务（复用现有 worktree 执行链，不另起引擎）。
- `tasks/merge.rs` 的 premerge/run_and_gate：增 acceptance 校验环节，结果写 `acceptance_result_json`。
- 前端 `Audit.tsx`：CR 审核页展示 acceptance 清单 + 自动校验结果 + 人工勾选未自动项。

### 4.5 工作量 / 风险

- 约 4–5 天。风险中：自动补测试可能产生低质测试 → 补测试也要过审（不静默合并）；测试缺口检测先保守（只对 High 风险触发），避免拖慢流水线。

## 5. CI/CD 与发布闭环 — P1

### 5.1 现状缝隙

记忆「合并并行化」「自指合并闪退与自更新」：合并止于 `git merge --squash` 到 dev（`merge.rs`，每 CR 压一个提交），并 push origin/dev。已有 revert 回滚 merged。**缺**：dev → main 的发布流程、部署触发、发布后回归/灰度/回滚策略。当前 main 受 GitProxy 保护（禁 push main），发布需走受控通道。

### 5.2 设计决策：发布作为"第三类受控流水线"，不破坏双审核与 Git 安全

- **发布单（Release）= 一批已合并到 dev 的 CR 的集合**，经"发布审核"（第三闸，可选，默认开）→ 执行 dev→main 的受控合并（仍经 GitProxy，唯一入口，类比 review_2）→ 触发部署命令（项目级配置，类似 run-config 的 test/build 命令）。
- **部署命令外置**：`run-config.json` 加 `deploy` 命令段（栈画像可预填，记忆「多栈适配」），AutoForge 只负责受控触发 + 落日志（复用代码 Agent 执行日志机制，记忆「代码Agent执行日志」），不内置具体云厂逻辑（保持零外部依赖哲学）。
- **回滚**：复用现有 revert + 记录发布快照 sha，一键回退 main 到上个发布点（仍经 GitProxy 白名单的受控 force 通道，单独审计）。

### 5.3 数据模型 / 迁移

```sql
-- 0074_release.sql
CREATE TABLE releases (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  status TEXT NOT NULL,          -- pending_release_review | deploying | released | failed | rolled_back
  cr_ids_json TEXT NOT NULL,     -- 纳入本次发布的 CR
  dev_sha TEXT, main_sha TEXT,   -- 发布前后快照，供回滚
  notes TEXT, created_at TEXT NOT NULL, released_at TEXT
);
```

### 5.4 改动点

- 新增 `tasks/release.rs`（受控 dev→main 合并 + 部署命令触发，纯 Rust，事件走 sink）。
- `core/git.rs::GitProxy`：为发布开一条**受控的 main 合并通道**（仍拦截裸 push main / force，仅允许"发布流水线 + 已审核"路径，类比 review_2 是 merge 唯一入口）。
- 新增 `commands/releases.rs`（创建发布单 / 发布审核 / 触发 / 回滚）+ 注册 + services 封装。
- 前端：新增「发布」视图或在 Audit/Dashboard 加发布区（遵循 page_architecture 划分）。

### 5.5 工作量 / 风险

- 约 5–7 天。风险**高**（碰 main 分支）：必须保持 GitProxy 唯一入口铁律，发布审核默认开，全审计，回滚先演练。建议先做"只合并到 main、不自动部署"的最小闭环，部署命令二期接。

## 6. 多人 / 团队协作 — P2（依赖 #1）

### 6.1 现状缝隙

记忆「操作者身份卡+通知收件箱」：现为**单操作者**（rail-me 身份卡存 `app_settings`，通知 0042）。要支持团队，需要：多操作者身份、审核人路由、任务/审核分配、操作审计区分"谁做的"。这依赖 #1 后端独立化（多人意味着多客户端/Web 接入，桌面单进程模型不够）。

### 6.2 设计决策：先做"身份与归属"，不急做权限矩阵

- **身份**：从单 operator 升为 `operators` 表（多条），登录/选择身份（桌面期可简单切换，Web 期接真实鉴权）。
- **归属与审计**：审核动作（review_1/review_2）、合并、发布记 `actor_id`，时间线可追溯"谁批的"。
- **路由（可选二期）**：按项目/标签把待审 CR 路由给指定审核人，通知收件箱按人过滤。
- **权限矩阵**：MVP 不做复杂 RBAC，先两档（操作者/只读观察者），后续再细化。

### 6.3 数据模型 / 迁移

```sql
-- 0075_operators.sql
CREATE TABLE operators (id TEXT PRIMARY KEY, name TEXT, email TEXT, role TEXT, created_at TEXT);
ALTER TABLE change_requests ADD COLUMN review1_actor_id TEXT;
ALTER TABLE change_requests ADD COLUMN review2_actor_id TEXT;
-- 通知表 0042 已有按人字段则复用，否则加 operator_id
```

### 6.4 改动点 / 工作量 / 风险

- 改动点：身份选择 UI（rail-me 扩展）、审核命令记 actor、通知按人过滤。
- 约 1 周+（且强依赖 #1 完成后端独立 + 鉴权，否则只能做桌面端"假多人"）。风险高（鉴权/越权），建议放在 #1 落地、且有真实 Web 入口需求后启动。

## 7. Schema 驱动学习闭环推广 — P2

### 7.1 现状缝隙

记忆「Schema 驱动 Agent」：版本化 schema = 执行标准 + 优化记录 + 优化杠杆；脚手架 `agents/schema.rs` + 统一 `agent_outputs` 表（0040）+ trace 下钻已就绪，**但只在 analysis/test 两个样板落地**，triage/proposer/grader/summarizer 等仍未纳入。学习闭环（记忆「Innate 记忆召回」「Schema 驱动」）的杠杆未充分释放。

### 7.2 设计决策：把样板模式逐角色推广 + 加 A/B 评测位

- **推广**：按 schema.rs 既有脚手架，给 triage/proposer/grader 各定义版本化 schema + 落 `agent_outputs`，零新表。
- **A/B 评测**：同一输入用两个模型/两版 prompt 跑，记录到 agent_outputs + trace，人工或规则打分，沉淀"哪个版本更好"——把"优化记录"变"优化决策"。
- **闭环接入**：评测结果回灌 Innate（记忆「Innate 记忆召回」校准回路），形成"标准 → 度量 → 改进"循环。

### 7.3 改动点 / 工作量 / 风险

## 8. 多仓 / monorepo 编排 — P2

### 8.1 现状缝隙

`projects` 表以单仓为单位（repo_path / branch_dev / branch_main）。跨项目依赖（A 改了 B 依赖的接口）、联动改动、统一发布目前无感知。

### 8.2 设计决策：先做"项目关系图 + 联动提示"，不急做跨仓原子提交

- **关系图**：`project_links` 记录项目间依赖（A depends_on B），人工或扫描建立。
- **联动提示**：某 CR 改动命中"被依赖接口"时，提示"可能影响下游项目 X"，在下游建关联需求（不自动改，交人审）。
- **monorepo**：对单仓多包，复用栈画像（记忆「多栈适配」）做包级影响面，按包并发执行。
- **跨仓原子发布**：远期，依赖 #5 发布闭环成熟后再议。

### 8.3 数据模型 / 改动点 / 工作量 / 风险
