## 0. 核心判断（先对齐，再看细节）

读完 10 条痛点并交叉核对代码现状，结论是：

> **这 10 条痛点 AutoForge 大多已有「引擎」，但缺「成品」。** 真实差距不是从零造功能，而是三件事：
> 1. **收口**——把散落能力串成一条「人能签字放行」的链路；
> 2. **外显**——把后台已发生的事做成相关方看得见、可演示的界面/产物；
> 3. **闭环**——把断点接上（反馈→需求、需求→代码→测试→批准的可追溯证据链）。

因此本方案按 **`现状(file 证据) → 真实缺口 → 任务`** 组织，而非 greenfield 重造。

### 一个高杠杆收口点（贯穿全案）

P3 / P8 / P7 / P10 / P5 的「外显」需求**全部汇聚到同一个「改动溯源单页」**：一屏串起
`需求原文 → 分析结论/风险 → 选用模型 → 影响面预查 → 执行日志摘要 → Diff → 测试结果 → 双闸口批准 → 相关历史经验`。
它一次性落地 P3+P8，并为 P5/P7/P10 提供外显载体——**单点投入、多痛点收口**，建议作为 Phase 1 旗舰交付。

## 2. 逐条实施方案

### P1 · 预览交付慢

- **现状**：分支启动预览 + worktree 隔离 + node_modules 软链 + 预览日志事件化（`commands/cr_preview.rs`、`commands/dev_server.rs`、`AppEvent::PreviewLog`、前端 `LiveLogModal`）；栈画像自动预填预览命令（`core/stack.rs`）。引擎已能「一分支一预览」。
- **真实缺口**：
  1. 预览仅在**操作者本机审核页**可见，非技术相关方（产品/客户）拿不到 URL/QR；
  2. 预览是「按需手点启动」，非「改完即起」；
  3. 多预览端口/生命周期无总览。
- **任务**：
  - `P1-1` 预览**对外分享**：为运行中预览生成可分享链接/QR（局域网 host 或隧道），相关方扫码即看。复用微信小程序预览已有 QR 通路（见 `specs/stack_expansion_roadmap.md` 的 weixin_preview_mode）。
  - `P1-2` `review_2` 进入「待代码审核」时**自动拉起预览**（可配置开关），把「改完→看见」压到零手动。
  - `P1-3` 预览总览面板：列出当前所有活跃预览（项目/分支/端口/状态/分享链接），统一启停。

### P2 · 需求多、人工成本高、开发周期长

- **现状**：自主产线（`tasks/autosupply.rs` 自喂料 + `intake/proposer.rs` 深度提议 + `intake/gateway.rs` triage 解耦）+ 并发槽位（`core/concurrency.rs`）+ 幂等执行（`job_executions`）。「按产出」的引擎在。
- **真实缺口**：
  1. 缺**单位经济外显**——没有「这条需求消耗多少 token/时长/成本 vs 人工工时」的对比看板，决策者看不到「按工时→按产出」的塌缩；
  2. 长尾 backlog 的吞吐率不可见。
- **任务**：
  - `P2-1` 单位需求成本卡：聚合 `llm_traces` 的 token/时长/模型成本，按 issue→CR 汇总，Dashboard 出「单位需求边际成本」与累计节省工时估算。
  - `P2-2` 产线吞吐看板：每日/每周完成 CR 数、平均周期、并发占用率、backlog 消化速度。
  - `P2-3`（可选）排序策略外显：把 proposer/triage 排序依据做成可解释卡片（呼应「传送带自排序」愿景）。

### P3 · AI 黑盒，不敢拥抱全自动编码 — **Phase 1 核心**

- **现状**：两道人工闸口（`review_1`/`review_2`）+ Diff/变更摘要/测试结果 + LLM 全链路 trace（`core/trace.rs`、`llm_traces`）+ 代码 Agent 执行日志实时滚动（`AppEvent::CodeAgentLog`，迁移 0064）+ Git 护栏 + 单一合并入口。**透明度引擎几乎全有。**
- **真实缺口**：证据**分散在多个 tab**（Trace 页 / 执行日志 tab / Audit Diff），没有一个「**这次改动从何而来**」的**单一可签字视图**。
- **任务**：
  - `P3-1` **改动溯源单页**（旗舰交付）：在 Audit 给每个 CR 一条溯源时间线——需求原文 → 分析结论/风险 → 选用模型 → 执行日志摘要 → Diff → 测试结果 → 双闸口批准记录，一屏纵览。数据全为现成表 JOIN（`issues`/`issue_analyses`/`change_requests`/`worktree_sessions`/`llm_traces`/`cr_test_runs` + 代码 Agent run logs）。
  - `P3-2` 「为什么这么改」摘要：从执行日志 `## 改动摘要`（`extract_report`）+ 分析理由提炼成人类可读的放行说明，挂在批准按钮旁。
  - `P3-3` 信任度红绿灯：放行前展示「测试是否全过 / 是否触碰高风险文件 / 是否有安全审计告警」三色指示。

### P4 · 部署运维成本大

- **现状**：架构层面已天然解决——桌面端一体机、SQLite 本地库、进程内 Tokio 队列、零外部依赖、数据不出本地、密钥系统钥匙环加密（`core/secrets.rs`）。
- **真实缺口**：
  1. **最强卖点却最不外显**——无界面/文档把「零运维」讲清楚；
  2. 打包分发/自更新链路缺正式发布产物（已有 Settings「同步更新」ff-only）。
- **任务**：
  - `P4-1` 「零部署」说明页/onboarding：首启展示「无需服务端/无需云/数据本地」事实清单（低成本高回报，主要是文案 + 一屏 UI）。
  - `P4-2` 打包发布流水线收口：`npm run tauri:build` 三端产物 + 自更新通道验证（呼应跨平台改造）。
  - `P4-3`（可选）本地资源占用看板：当前在跑几个 worktree/几个预览/CPU，佐证「运维≈0」。

### P5 · 缺乏需求反馈收集路径 — **Phase 1**

- **现状**：反馈 Widget + 可吊销 token（`commands/widget.rs`，迁移 0041）+ 进程内限流（`core/ratelimit.rs`）+ 8 类通知通道 + 需求传送带 triage 池。「采集」已通。
- **真实缺口**：反馈进了 triage 池，但**到「自动成为可执行需求」之间仍半自动**；且无「反馈来源→已交付改动」回链，使用者看不到反馈被采纳。
- **任务**：
  - `P5-1` 反馈→需求自动化：Widget/通道进来的反馈走 proposer 自动起草为 issue 候选（补「反馈源」lens 与 provenance 字段）。
  - `P5-2` 反馈闭环回链：issue/CR 记录反馈来源 id，交付后向来源回执「你的反馈已上线」（复用通知通道）。
  - `P5-3` 反馈来源看板：按来源/项目统计第一手反馈量与转化率。

### P6 · 需求方无法精准描述需求

- **现状**：孵化台（blueprint→孵化台，`commands/blueprint.rs`，迁移 0074；Studio draftId-keyed）+ 分析 Agent 自动澄清 + 多 Agent 会议室共建 + Express CR 直通执行。「模糊→规格」引擎在。
- **真实缺口**：
  1. 缺**对需求方友好的引导式澄清**（结构化提问，而非要他写 PRD）；
  2. 孵化产物到「可执行规格」的质量校验缺标准。
- **任务**：
  - `P6-1` 引导式澄清问卷：分析 Agent 主动生成 3–5 个澄清问题（缺口/边界/验收），需求方答题即补全规格。
  - `P6-2` 规格就绪度检查：对孵化产物做「可执行性」打分（验收标准/影响范围/约束齐全度），不达标提示补全后再进 review_1。

### P7 · 知识沉淀流失，人走带走 — **Phase 3**

- **现状**：Innate 经验记忆 + 召回校准回路（`kb_recall_traces`）+ LLM 全链路 trace 留痕 + `.autoforge/docs` 决策/产物沉淀 + 记忆文件层（`memory/`）。
- **真实缺口**：
  1. 「why」沉淀**被动**，依赖 Agent/人主动记；
  2. 沉淀知识与具体 CR/需求的回链弱，检索时拿不到上下文。
- **任务**：
  - `P7-1` 决策自动捕获：在 review_1/review_2 批注、AI 解冲突、执行失败重试这些「决策点」自动落一条结构化 insight（why + 当时上下文 + 关联 CR）。
  - `P7-2` 知识↔CR 双向回链：Innate chunk 关联 issue/CR id，溯源单页（P3-1）可展开「相关历史经验」。
  - `P7-3` 部落知识体检：Trace/Innate 健康面板增加「覆盖率」（多少 CR 有 why 沉淀）。

### P8 · 需求↔代码↔测试 可追溯性断裂 — **Phase 1（与 P3-1 合并交付）**

- **现状**：链路数据已贯通——`issues → issue_analyses → change_requests → worktree_sessions → llm_traces → cr_test_runs`，双闸口审批记录在 `change_requests.admin_decisions`。
- **真实缺口**：**有链路数据，无追溯产品**——没人能一键回答「这段代码为哪条需求存在、对应哪个测试、谁批准的」。
- **任务**：
  - `P8-1` 可追溯证据链 API：给定 CR/issue/文件，返回完整链（需求→代码 hunk→测试→批准人/时间）。底层现有表 JOIN，无新表。
  - `P8-2` 「代码→需求」反查：Diff 视图里任一改动文件可反查「属于哪个 CR、哪条需求」（合并入 P3-1 溯源单页）。
  - `P8-3` 可导出审计报告：证据链导成只读 markdown/PDF 供合规/交接，落 `.autoforge/deliverables/`。

### P9 · 快交付埋雷，技术债与质量不可控 — **Phase 2**

- **现状**：强制测试（merge 前 `run_and_gate`，失败阻断）+ 代码审计/安全审计 skill（`autoforge-audit-scan`/`code-audit-scan`）+ premerge/land 拆分（迁移 0066）+ security 门（cargo audit）。
- **真实缺口**：
  1. 质量门是「测试过/不过」二元，缺**技术债的可见与量化**；
  2. 审计是「按需 skill」，未作为**产线强制阶段**自动跑并阻断。
- **任务**：
  - `P9-1` 质量门产线化：把 code-audit/security-audit 作为 review_2 后的**自动阶段**，产出结构化结论（沿用 `agent_outputs` schema），高危阻断合并。
  - `P9-2` 技术债面板：聚合 clippy/审计告警/复杂度，给项目「债务趋势」曲线。
  - `P9-3` 质量底线即约束：阈值（覆盖率/告警数/高危文件触碰）做成项目级可配置门，不达标 review_2 不可放行。

### P10 · AI 改动缺全局上下文，局部对、全局错 — **Phase 2**

- **现状**：执行前 code-intel 预查（`agents/tools/code_intel.rs`，符号定位/调用者/影响面，push 式三家一致）+ 项目上下文与规格注入 + 栈画像感知（`core/stack.rs`）+ codegraph MCP。
- **真实缺口**：
  1. 预查能力槽位**硬编码**（locate_symbol/find_callers/impact_analysis），影响面深度有限；
  2. 预查结果**不外显**——人看不到「AI 改动前看清了哪些全局影响」，无法佐证「顾全大局」。
- **任务**：
  - `P10-1` 影响面外显：把 code-intel 预查到的「调用者/影响文件/受影响测试」作为证据挂到溯源单页（P3-1）。
  - `P10-2` 预查覆盖增强：补「是否违反既有约定/规格」的预查 lens（结合 specs 注入），把违约风险前置。
  - `P10-3`（需 Rust 改）能力槽位可扩展：硬编码槽位改为配置驱动，便于接更强影响分析 MCP。

## 4. 全局约束（落地时遵守，将带入 tasks.json）

- 迁移仅追加不改已有；新增 command 四步：`commands/<m>.rs` → `mod.rs` 导出 → `lib.rs` 注册 → `services/index.ts` 封装，前端禁直接 invoke。
- 业务逻辑零 Tauri 类型（CLAUDE.md 铁律#1）；事件只走 `event::emit(app, AppEvent)`。
- 前端只用 `src/index.css` CSS 变量，禁硬编码色值/px；图标走 `<Icon/>`；下拉用 `proj-select+mention-pop`，禁原生 `<select>`；每屏 ≤1 主按钮。
- 外部输入回灌前过 `core/security::has_obvious_injection()`；git 走 GitProxy。
- 涉及 IPC/进程/文件须在 `npm run tauri:dev` 完整环境验证。
