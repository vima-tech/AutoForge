# 共享上下文优化（Shared-Context Optimization）设计方案

> 目标：夺回 Claude Code 这类 agent 工具的**核心优势——一个 session 连续处理多个需求时，
> 代码库探索成果 / 已建立的理解被持续复用**。AutoForge 当前「一个 CR 一个冷启动 worktree +
> 一次性 `claude --print`」的模型把这份成果每次丢弃重来。
>
> 本文是 [`同文件多需求合并.md`](./同文件多需求合并.md) 的**上位方案**：合并文档解决一个特例
> （同文件 → 一次执行），本方案推广到它漏掉的维度，复用其同一套数据模型。**先不修改代码，仅出设计。**

---

## 0. 先把成本模型校准对（决定后面所有取舍）

很容易把「上下文税」误记为「每次重读 `CLAUDE.md`/specs」——但那部分本就在 prompt 里、是廉价的字符串拼接
（`build_prompt`，`mod.rs:449-459`）。**真正贵、且当前完全没有回收的，是 agent 进程内的「代码库探索」**：
开文件、grep、追调用链、在脑子里建模——这部分发生在 claude 进程内（`cli.rs:165` 的 `--print` 会话），
进程一退出就蒸发，下一个 CR 从零再来。

| 成本项 | 贵不贵 | 当前回收了吗 | 本方案如何处理 |
|--------|--------|--------------|----------------|
| 重读 CLAUDE.md/specs 拼进 prompt | 便宜 | 每次重拼（无所谓） | 不优化 |
| **agent 探索代码库建心智模型** | **最贵** | **零回收** | 轴 B：把它本会探索到的东西预先喂进去 |
| 同模块 N 需求各跑一遍探索 + 共享文件撞车 | 贵 ×N + 冲突 | 各自冷启动 | 轴 A：装进同一会话，探索摊销 + 免冲突 |
| code_intel 符号定位（已注入） | 中 | 每 CR 重查（主仓索引在） | 轴 B 扩展它，已是正确的钩子 |
| Innate 历史经验召回（`execution.rs:227`） | — | **已做对**（跨会话记忆） | 保持 |

**校准结论**：优化的靶心是「**减少 agent 探索**」和「**别让相关需求各自重复探索同一片代码**」，
不是省那点 prompt 重拼。下面两条轴都瞄这个靶。

### 0.1 先量再改（S0，最该前置）

整个方案的前提是「探索很贵」。这个前提**可以低成本实测**：`cli.rs` 已经解析 claude 的 stream-json
事件（工具调用 / 文件编辑 / 助手发言，`cli.rs:166-175`）。给每个 CR 的执行落一组指标——

- 工具调用次数、文件读取次数（探索强度的代理指标，从已解析的 stream-json 数）；
- 总 token / 墙钟（已有 `duration_ms`，`execution.rs:495`）；
- 后续 review_2 是否要求迭代、是否产生合并冲突（返工率）。

**先建基线，再让每个优化对账**（探索轮次降了吗？墙钟降了吗？）。否则全是信仰。这一步几乎零新基础设施
（复用现有 stream-json 解析 + `code_agent_run_logs` 落库），是最高性价比的第一步。

## 1. 两条正交的共享轴

| 轴 | 含义 | 合并文档覆盖了吗 |
|----|------|------------------|
| **轴 A · 空间共享（intra-session）** | 把多个**强耦合**需求塞进同一会话，探索摊销 + 免冲突 | 只覆盖 L0（同文件硬合并），且**已部分落地** |
| **轴 B · 时间共享（cross-session 温启动）** | 把 agent 本会探索到的东西预注入，缩短每个 CR 的探索 | 完全没覆盖 |

> 合并文档的 `merged_requirements` 多需求同 prompt 批处理**已在 `execution.rs:264-306` + `build_prompt`
> （`mod.rs:411`）落地**。所以轴 A 的"机制"已有，本方案的增量是**聚类信号**和**何时该批 / 何时别批**。

**关于用户原话「一个 session 处理多个需求」**：字面实现就是 §5 的 **S4 claude 会话续接**——让同一个
agent 进程带着对话历史与 KV-cache 连续做多个需求。但它依赖 CLI 无头续接能力（当前 `--print` 无）且要
重排状态机/并发/回收，风险与周期都最高。本方案的立场是：**轴 A（批处理）+ 轴 B（预注入）以低得多的
风险、早得多的交付，拿到 S4 大部分的实际价值（探索复用 + 免撞车）**，而非回避 S4——S4 作为研究项并行推进。

## 2. 轴 A —— 上下文亲和批处理（推广合并文档）

### 2.1 关键前置：批处理不是免费的——并行度的取舍

把 N 个需求装进一个会话 = **占 1 个并发槽而非 N 个、且组内串行**。机器有空闲槽时，
**N 个并行冷启动的墙钟，可能短于 1 个串行温会话**。所以批处理**不是无脑越多越好**——它是用并行度
换「探索摊销 + 免冲突 + 一次审核」。

**决策规则（只在以下成立时才批）**：

| 条件 | 该批吗 | 理由 |
|------|--------|------|
| L0 共享实质文件（会撞车） | **必须批**（硬合并） | 分开执行 = 合并冲突，正确性问题压倒并行度 |
| L1 同模块且并发槽紧张 | 倾向批 | 省下的槽 + 摊销探索 > 串行损失 |
| L1 同模块但有空闲槽 | **倾向不批** | 并行冷启动墙钟更短，靠轴 B 温启动消除重复探索更划算 |
| 仅 L3 同项目、无文件/模块耦合 | **不批** | 装一起只会稀释注意力、放大 blast radius；交给轴 B |

> 即「**强耦合才批，弱耦合靠温启动**」。轴 A 治撞车，轴 B 治重复探索——别让轴 A 去硬扛轴 B 的活。

「槽紧」可锚到真实并发状态量化，不靠拍脑袋：并发槽 `Semaphore` 默认上限 5、`pending_review` 阈值 20
（`core/concurrency.rs`、testing 规格）。以**执行前可读的 `available_permits`** 为信号——可用槽接近 0 时
偏向批（省槽），槽充裕时偏向并行。阈值上线后用 S0 的墙钟数据回调。

### 2.2 亲和分级（聚类信号，扩 L1/L2）

合并文档按**共享文件**聚类。扩成分层信号，但落地时配合 §2.1 决策规则：

| 层 | 信号 | 探测成本 | 默认动作 |
|----|------|----------|----------|
| **L0 共享文件** | `affected_files` 交集 ≥1 实质文件 | 低（集合交） | 硬合并（合并文档） |
| **L1 同模块/目录** | 同目录 / 同 crate | 低 | 按 §2.1 决策（槽紧才批） |
| **L2 符号邻域（codegraph）** | 各需求点名符号互为调用者/被调用/影响面邻居 | **中，需限界（见下）** | 提示强相关，多为软批处理候选 |

**L2 成本必须限界**：对 pending 队列做两两 impact 比较是 O(N²) 图查询。约束：仅在 L1 已同模块的小集合内
再跑 L2 细分（先用便宜的 L0/L1 把候选缩到个位数，再对这几个跑 codegraph），不在全队列裸跑 L2。

沿用合并文档的**枢纽文件降权**（`lib.rs`/`services/index.ts`/`mod.rs`/迁移目录）与**团（clique）语义**
（全体共享同一信号，拒绝传递性串联），避免虚假大簇。

### 2.3 硬合并 vs 软批处理（诚实分期）

| 语义 | 适用 | 产物 | 状态 |
|------|------|------|------|
| **硬合并** | L0 会撞车 | 1 worktree → **1 diff → 1 CR → 1 审核** | 合并文档已规划；本方案 MVP 直接复用 |
| **软批处理** | L1/L2 共享上下文但不撞车，期望**逐需求独立可审/可回滚** | 1 会话，逐需求独立成 diff | **Phase 2+**，见下 |

**诚实交代软批处理的难点**：claude 被禁 `Bash(git *)`（`cli.rs:179`），agent 无法自己打 commit 分界，
只能靠报告里声明的「需求 #k 改动文件清单」后置切分 diff——存在改动外溢误切风险。因此：

- **MVP 不做软批处理**，轴 A 只上 L0/L1 硬合并（出 1 个 CR，靠合并文档的 `split_change_request` 兜底拆回）。
- 软批处理列 Phase 2：先稳定「逐需求文件边界协议」+ 外溢检测（改动落在未声明文件 → 标红交人工），再开后置拆分。
- 不在 MVP 假装软批处理存在——否则它和硬合并无区别，"不连坐"是空头支票。

### 2.4 触发与人工闸门

完全继承合并文档：**系统探测候选 → 需求审核闸呈现 → 人工点头**；不做 AI 静默捆绑无关需求。
差异仅在探测信号扩 L1/L2，且合并面板显示「为何建议批 / 当前并发槽占用」帮操作者判断（呼应 §2.1）。

## 3. 轴 B —— 缩短探索：预注入 + 相关性门控

让**每个** CR（含无法批处理的孤立 CR）少探索：把 agent 本会自己 grep/读出来的东西，预先喂进 prompt。

### 3.1 两个杠杆

**杠杆 1 · 扩展 code_intel 预查（已是正确的钩子）。** `code_intel::locate_context`（`execution.rs:257`）
已把分析点名的符号定位到 file:line 注入。扩展它多带回 agent 否则要自己探索的东西：目标符号的**直接
被调用者 / 关键调用者签名 / 同文件相邻定义**。这直接砍掉 agent 开局的「这个函数在哪、谁调它」探索。
配置驱动（沿用现有 MCP code-intel 机制），best-effort，无则空串、零回归。

**杠杆 2 · 相关性门控的「近期改动摘要」（零 LLM）。** 注入**只与本 CR 文件相关**的近期已合并改动——
让新 CR 知道「我要动的这几个文件，最近哪个需求因为什么动过」。关键约束：

- **零 LLM**：摘要 = `已合并 issue 标题 + 该 CR 实际改动的文件清单`，全是现成数据，不跑模型、不截 agent 报告全文。
- **文件清单用哪份要分清**：历史改动取**实际合并 diff 的文件清单**（`compute_worktree_diff` 的真实结果，
  非分析估计）；当前 CR 在执行前只有**分析估计的 `scope.affected_files`** 作门控键。即「估计的本 CR 文件」
  ∩「历史的实际改动文件」——估计不准时门控会偏松/偏紧，可接受，配 S0 观测。
- **相关性门控**：只列与当前 CR 文件**有交集**的历史改动，**不无差别灌全项目改动史**（见 §3.2 负空间）。
- 硬字节上限：≤ 最近 N 条（如 8 条）、每条一行。
- **安全**：issue 标题源自外部需求 → 注入前过 `has_obvious_injection()`（安全规则第 1 条），视为不可信输入。

> Innate 召回（`execution.rs:227`）覆盖「过程性经验/技能」；杠杆 2 补「**这片代码近期的事实变更史**」，
> 互补不重叠。且杠杆 2 **故意不走 Innate**——它要的是廉价、纯事实、零策展开销的即席查询，不进知识库回路。

### 3.2 负空间：什么时候**不要**共享上下文（一等约束）

共享上下文会反噬——更大的 prompt 稀释注意力、混入无关信息把 agent 带偏。因此：

- 近期改动摘要**按文件相关性门控**，无交集不注入；
- 轴 A 弱耦合（仅 L3）**不批**（§2.1），不为"共享"而硬凑；
- 跨项目**绝不**共享；
- 注入预算硬上限，宁缺毋滥。

### 3.3 对 prompt 缓存的诚实下调

claude CLI 的 prompt cache 是**短 TTL（约 5 分钟）、进程内**的——**跨 CR 几乎命中不了**，不能指望它做
跨需求复用。把稳定内容（specs/CLAUDE.md/预注入）排在 prompt 前部仍是好习惯（结构清晰、单进程内多轮工具
调用可命中），但**别把它当作跨 CR 共享上下文的手段**。这条收益小，附带做即可，不作为卖点。

## 4. 与合并文档的衔接（复用底座，不重复造）

| 合并文档已规划/已落地（直接复用） | 本方案增量 |
|------|------|
| `change_request_issues` 表（0070）+ primary/member | 软批处理沿用（Phase 2） |
| `cr_issue_ids` helper | 复用 |
| `build_prompt` 的 `merged_requirements` 段（已落地，`mod.rs:411`） | 复用 |
| 候选探测 + 人工闸门 + 枢纽降权 + clique | 探测信号扩 L1/L2，叠加 §2.1 决策规则 |
| `split_change_request` 拆回 | 硬合并 MVP 的兜底 |

**统一底座**：轴 A 的聚类、轴 B 的近期改动摘要，都依赖同一个「**文件 → 动过它的 issue/CR**」反查。
**先按需 JOIN 查询**（CR 量在桌面 SQLite 下不大，`change_requests` ⋈ 改动文件清单实时查足够），
**实测慢了再物化成增量索引**——不要一上来就建 event 驱动的物化表，避免过度设计。两条轴共用这一份反查逻辑。

**衔接次序**：合并文档（建表 + L0 硬合并）先合入打底；本方案在其上**零 schema 变更**叠加 L1/L2 信号、
轴 B 预注入、决策规则。

## 5. 实施阶段（按 价值/风险 排序，度量前置）

- **S0 · 探索度量**：复用 stream-json 解析落「工具调用数/文件读数/墙钟/返工」指标，建基线。最低成本、解锁后续对账。
- **S1 · 轴 B 预注入**：扩 code_intel（杠杆 1）+ 相关性门控近期改动摘要（杠杆 2）。独立见效、低风险、直砍探索；
  用 S0 指标验证「探索轮次是否下降」。
- **S2 · 轴 A 硬合并扩 L1**：在合并文档基础上加同模块信号 + §2.1 决策规则（槽紧才批）。治撞车 + 摊销探索。
- **S3 · 轴 A 软批处理 + L2 codegraph**：逐需求边界协议 + 外溢检测 + 后置拆分；L2 限界聚类。
- **S4 · claude 会话续接（研究项）**：真正「一个 session 多需求」需 CLI 支持无头 `--resume`（**当前 `--print`
  无续接，需先验证版本能力**），且要解决与 CR 状态机/并发锁/超时回收（`reaper.rs`）的对齐。不阻塞前序。

## 6. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 批处理换掉并行度反而更慢 | §2.1 决策规则：强耦合才批，有空闲槽的弱耦合保持并行；用 S0 墙钟数据校准阈值 |
| 软批处理后置拆分误切（改动外溢） | MVP 不做软批处理；Phase 2 先上文件边界协议 + 外溢标红交人工 |
| 近期改动摘要稀释注意力/误导 | 相关性门控（仅交集文件）+ 字节上限 + 零 LLM 只列事实（§3.2 负空间） |
| 注入文本污染（issue 标题含注入） | 注入前过 `has_obvious_injection()` |
| L2 codegraph 聚类 O(N²) 爆炸 | 仅在 L0/L1 缩出的小集合内跑 L2，不全队列裸跑 |
| 整组 review_2 退回连坐 | MVP 硬合并设组内需求/总文件上限 + `split_change_request` 拆回；软批处理（Phase 2）逐需求独立可回滚 |
| 会话续接与状态机/并发/回收冲突 | 列研究项；不动现有无头一次性主路径；续接失败回退冷启动 |
| 加深 Tauri 耦合 | 索引刷新/注入全为纯 Rust async fn，事件只走 `AppEvent`（后端独立化铁律 1–4 条） |

---

## 7. 一句话总结

合并文档治「同文件撞车」。本方案校准靶心为**回收 agent 探索成本**，两招：
**轴 A** 只在**强耦合**时把需求装进同一会话（摊销探索 + 免冲突，且认账它牺牲并行度，靠决策规则取舍）；
**轴 B** 把 agent 本会探索到的东西（扩展 code_intel + 相关性门控的近期改动摘要，零 LLM）预注入每个 CR，
缩短探索。一切先经 **S0 度量** 对账，复用合并文档关联表 + 统一文件反查索引，零 schema 重写。
