# AutoForge 灵活方法论与上下文基质 · 设计文档

> 状态：设计（不含实施计划）
> 版本：v0.1 · 2026-07-01
> 定位：这是 AutoForge 相对通用编码 Agent（Claude Code / Codex / Cursor）的**核心错位**所依托的产品与架构设计。
> 本文只描述"要什么、为什么、结构长什么样"，**不含分阶段落地计划**。

---

## 0. 一句话

**方法论不是一个要被管理的实体，而是"物料随处可造、上下文随处可取"这个底层能力之上，由每个人按自己的工作习惯自然长出来的东西。**

AutoForge 的职责不是规定"该怎么开发"，而是把一切工作过程中产生的信息——需求、原型、文档、会议室聊天、编码 Agent 日志、trace、CR、审核意见——都变成**可被任意环节按需取用的物料/上下文**，让每个角色在自己收敛的界面里，用自己习惯的路径，把最准确的上下文喂给 Agent。

---

## 1. 设计哲学：三条不可动摇的原则

### 原则一：方法论是虚拟概念，不建实体、不做管理台

- **不做**"方法论"这个数据库表、不做"方法论编辑器"、不做"方法论市场"。
- 方法论 = 一个人在完成任务时**实际走过的物料创建与上下文取用路径**。
- 例：
  - A 习惯"先让设计 Agent 出原型图 → 人看图确认 → 再让编码 Agent 依原型开发"；
  - B 习惯"什么都不看，直接把需求丢给编码 Agent"；
  - C 习惯"先开会议室拉产品/测试讨论 → 沉淀 PRD → 再进编码"。
- 系统对这三者**一视同仁**：它们只是"用了哪些物料能力、在哪些节点取了哪些上下文"的不同组合。系统提供能力，不提供也不强制路径。

> 反面案例（要避免）：把 goal-loop 那种"PRD→SDD→原型→可追溯矩阵"固化成唯一流水线。那是**一种**方法论，不是方法论本身。它应该是**可选的物料组合模板**，而不是系统骨架。

### 原则二：从根本上支持方法论的"建立"——物料随处可造、上下文随处可取

这是全文的技术核心。拆成两个能力：

1. **任何环节都能创建任何物料**
   - 物料类型不预设封闭集合；需求阶段能建原型，编码阶段能补文档，审核阶段能加约束说明，会议室里能顺手沉淀一份规格。
   - 创建动作不绑定在某个"正确的阶段"。

2. **任何环节都能取用之前创建的一切上下文**
   - 不只是显式物料（文档/原型/规格），还包括**过程信息**：
     - 编码 Agent 的执行日志（`code_agent_run_logs`，迁移 0064）
     - 会议室聊天记录（`messages`）
     - Agent trace 日志（`llm_traces`）
     - Agent 的历史输出（`conversation_task_runs`）
     - CR / issue / 审核意见 / 孵化台草稿
   - 目标：**让最准确的上下文，喂给 Agent 做最准确的判断**。上下文越准，Agent 判断越准，这是整个系统效果的杠杆。

### 原则三：用页面功能对角色收敛，让每个人只关心当下的工作

- 底层是"万物皆物料/上下文"的统一基质（宽而通用）；
- 上层是**按角色裁剪的界面**（窄而聚焦）：测试只看测试要看的，产品只看产品要看的，实施运维只看部署运维要看的。
- 同一份底层物料，在不同角色的页面里以不同的"取景框"呈现。角色不需要理解整个基质，只需要在自己的界面里完成手头的事。

> 三条原则的关系：**原则二是地基**（统一基质），**原则三是外墙**（角色收敛界面），**原则一是结果**（方法论作为涌现物，不必被设计）。

## 2. 现状盘点：上下文为什么现在是"割裂的筒仓"

当前 AutoForge 已经有大量"物料"和"过程信息"，但它们**分散在互不相通的子系统里**，且只有一小部分真正进入了喂给 Agent 的上下文装配。

### 2.1 已进入统一上下文装配的来源

`commands/project_context.rs::load_project_context_for_conversation` 是当前唯一的"上下文汇聚点"，它拼装：

1. 项目优先文件：`claude.md` / `agents.md`（自动读取仓库根）
2. Pinned 文件：`conversation_project_context`（每会话手动 pin 的只读文件）
3. 工作区文件：`.autoforge/{docs,specs,deliverables}` 清单（≤8KB 内联，超出只列名）
4. 项目规格：`project_specs`（`always` 全文注入 / `on_demand` 只给清单，Agent 用 `read_spec` 工具按需拉）
5. 会话消息快照：`build_context_snapshot`（最近 N 条 `messages`，≤24KB 保尾截断）

会议室编排 `orchestration.rs::execute_conversation_task` 和"会议室立即编码"`assemble_conversation_context` 都复用这条路径。

### 2.2 **游离在上下文之外**的过程信息（关键缺口）

以下都存在、都有价值，但**都没有**进入上面的装配路径，Agent 判断时看不到：

| 来源 | 表 / 位置 | 现状 | 缺口 |
|------|-----------|------|------|
| 物料库文件 | `material_files` / `material_folders` | 只在项目管理页展示 | 不进 Agent 上下文 |
| 编码 Agent 执行日志 | `code_agent_run_logs`（0064） | 只在审核页「执行日志」tab 展示 | 后续环节/其他 Agent 无法引用 |
| LLM/工具/MCP trace | `llm_traces`（core/trace.rs） | 只在 Trace 页按需筛选 | 无法回灌作为"上一次 Agent 怎么想的"上下文 |
| Agent 历史输出 | `conversation_task_runs.output_text` | 仅同一任务内累积 | 跨任务/跨会话不可取 |
| CR / issue / 审核意见 | `change_requests` / `issues` / admin_decisions | 各自页面 | 编码时看不到"人在审核里说过什么" |
| 孵化台草稿 | blueprint_*（0074） | 孵化台内 | 与会议室/CR 上下文不互通 |

### 2.3 结论

现状是"**装配点单一、但取材面狭窄**"：只有 5 类来源进了上下文，且大多是"静态文件"，几乎不含"过程信息"。要兑现原则二，核心工作是**把取材面从 5 类扩展到"全部物料 + 全部过程信息"，并让它可被任意环节按需装配**——而不是新增一堆管理台。

## 3. 核心概念模型：上下文基质（Context Substrate）

引入一个**统一的逻辑抽象**（注意：是逻辑抽象/视图，不是要求把所有表合并成一张表）：**Context Item（上下文条目）**。

### 3.1 Context Item 是什么

系统里一切"可以被喂给 Agent 的信息单元"都是一个 Context Item。它是对现有各表的**统一投影**，不改变各表的存储职责：

```
ContextItem {
  id            稳定引用（source_kind + source_id 派生）
  project_id    归属项目（跨项目隔离的边界）
  source_kind   来源类型：见下表
  source_id     在原表中的主键
  title         人可读标题
  created_at    产生时间
  origin_stage  产生阶段（requirement / design / chat / coding / review / ops …）
  origin_actor  产生者（user / agent-id / system）
  content_ref   如何取到正文（文件路径 / 表字段 / 懒加载器）
  size_hint     体积（用于装配预算）
  trust         信任级别（trusted / external_untrusted）→ 决定是否过注入闸
  labels        自由标签（供检索/取景框过滤）
}
```

### 3.2 source_kind 全集（把 2.2 的缺口全部纳入）

| source_kind | 底层来源 | trust | 备注 |
|-------------|----------|-------|------|
| `file_priority` | claude.md/agents.md | trusted | 仓库根自动 |
| `file_pinned` | conversation_project_context | trusted | 手动 pin |
| `workspace_doc` | .autoforge/docs | trusted | Agent 可写 |
| `workspace_spec` | .autoforge/specs | trusted | |
| `workspace_deliverable` | .autoforge/deliverables | trusted | |
| `project_spec` | project_specs | trusted | always/on_demand |
| `material` | material_files | trusted | **新纳入** |
| `chat_message` | messages | trusted | **过程信息** |
| `agent_output` | conversation_task_runs | trusted | **过程信息** |
| `code_agent_log` | code_agent_run_logs | trusted | **过程信息，新纳入** |
| `llm_trace` | llm_traces | trusted | **过程信息，新纳入** |
| `issue` | issues | trusted | 需求正文 |
| `cr_review` | change_requests + admin_decisions | trusted | 审核意见 |
| `incubator_draft` | blueprint_* | trusted | 孵化台 |
| `attachment` | conversation_attachments | trusted | 图片/文本/PDF |
| `mcp_result` | 运行期 MCP 工具输出 | **external_untrusted** | 必过注入闸 |
| `web_result` | web_search / deep_research | **external_untrusted** | 必过注入闸 |

> 设计要点：Context Item 是**读侧的统一视图 + 一层薄索引**，不是"把所有内容复制进一张大表"。正文仍留在各自表/文件里，通过 `content_ref` 懒加载。这样：
> - 不破坏现有存储与迁移；
> - 新增来源 = 新增一个投影适配器，不动既有子系统；
> - 与长期愿景一致（业务逻辑不依赖 Tauri，纯 Rust 投影层）。

### 3.3 一条铁律：信任分级贯穿基质

- 内部产生的 Context Item（chat/agent_output/log/trace/file…）为 `trusted`；
- 外部来源（MCP、web、外部 webhook 需求）为 `external_untrusted`，**回灌上下文前必过 `core/security::has_obvious_injection()`**。
- 这直接继承现有安全规则（见 CLAUDE.md 安全规则 1、原则 & `project_local_source_injection_exempt` 记忆里的豁免逻辑：本地源码读豁免注入闸，外部输入不豁免）。

## 4. 目标架构

四层，从下到上：

```
┌───────────────────────────────────────────────────────────┐
│  L4  角色收敛界面（原则三）                                  │
│      测试台 / 产品台 / 编码台 / 实施运维台 / 会议室 …         │
│      每个台子 = 一个"取景框 + 常用物料创建入口"              │
├───────────────────────────────────────────────────────────┤
│  L3  上下文装配引擎（原则二的动作侧）                        │
│      ContextRequest → 选材 → 预算 → 信任过滤 → 装配 prompt   │
├───────────────────────────────────────────────────────────┤
│  L2  上下文基质（原则二的数据侧）                            │
│      ContextItem 统一投影 + 检索/引用 + 信任分级             │
├───────────────────────────────────────────────────────────┤
│  L1  既有存储（不动）                                        │
│      messages / material_files / code_agent_run_logs /      │
│      llm_traces / project_specs / issues / change_requests… │
└───────────────────────────────────────────────────────────┘
```

### 4.1 L2 上下文基质（数据侧）

职责：把 L1 各表投影为 ContextItem，提供三种访问：

1. **枚举/检索**：按 `project_id + source_kind + labels + 时间窗 + 全文` 查出候选 Context Item（只回元数据，不回正文）。
2. **正文懒取**：按 `content_ref` 取单条正文（带体积上限，复用现有 2MB / 8KB / 24KB 等约束）。
3. **稳定引用**：`ContextItem.id` 可被消息块、CR、任务持久化引用，跨会话/跨阶段有效——这是"任何环节取用之前物料"的落点。

关键设计取舍：

- **投影而非搬迁**：适配器模式，每个 source_kind 一个 `impl ContextSource`。新增来源零迁移。
- **检索索引**：MVP 可用 SQLite FTS（对齐"零外部依赖"约束，禁止引入向量库/ES）。语义检索若需要，走可选 MCP 工具，不作为核心依赖。
- **纯 Rust**：基质层不得引用 `tauri::*`（对齐后端独立化愿景）。

### 4.2 L3 上下文装配引擎（动作侧）

把现在硬编码在 `load_project_context_for_conversation` 里的"拼哪些 + 怎么截断"抽象为**可配置的装配**：

```
ContextRequest {
  project_id
  scope_hint      当前工作对象（conversation_id / issue_id / cr_id）
  include         要纳入的 source_kind 集合（或"取景框"预设）
  refs            显式点名的 ContextItem.id（用户/上一环节指定）
  budget_bytes    体积预算
  purpose         用途（chat_reply / code_exec / analysis / review …）
}
        │
        ▼
ContextAssembler
  1. 收集候选（显式 refs 优先 + include 集合枚举）
  2. 排序（refs > 优先文件 > 规格 > 近期过程信息 > 其余）
  3. 信任过滤（external_untrusted 过 has_obvious_injection）
  4. 预算裁剪（保尾/保头按 purpose 定，复用现有 truncate_keep_tail / truncate_to_bytes）
  5. 渲染为 prompt 前缀（保留现有 "=== 项目文件: X ===" 风格）
        │
        ▼
  拼进 Planner / 编码 Agent / 分析 Agent 的 prompt
```

- 现有 `load_project_context_for_conversation` 成为 `ContextAssembler` 的一个**默认预设**（默认取景框），行为向后兼容——这是渐进改造的关键，不推倒重来。
- **"任何环节取用之前物料"= 让每个环节都能构造 `ContextRequest` 并塞 `refs`/`include`**。例如编码 Agent 执行时，不再只拿静态文件，而是可显式纳入"本需求相关的会议室结论 + 上一次编码日志 + 相关 trace"。

### 4.3 L4 角色收敛界面（原则三）

思路：**不为每个角色重造一套 App，而是给同一基质配不同"取景框（Lens）+ 常用物料创建入口"**。

取景框 = 一组默认的 `include` source_kind + 默认 labels 过滤 + 默认展示形态。

| 角色台子 | 默认取景框（看什么） | 常用物料创建入口（造什么） | 主要动作 |
|----------|---------------------|---------------------------|----------|
| 产品台 | issue / chat_message / incubator_draft / workspace_doc(PRD) | 需求、PRD、原型引用 | 提需求、审需求、沉淀 PRD |
| 设计台 | issue / 原型 material / workspace_doc | 原型图/设计稿（material） | 出原型、关联需求 |
| 编码台 | issue + 相关 doc/spec + 近期 code_agent_log + 相关 trace | 技术方案 spec、代码 | 触发编码 Agent、看执行日志 |
| 测试台 | cr / diff / testing spec / code_agent_log | 测试计划、用例、缺陷 | 看变更、跑测试、提缺陷 |
| 实施运维台 | cr / 部署配置 / 运行日志 / deliverable | 部署说明、发布记录 | 部署、回滚、观测（**当前最薄，见 §7**） |
| 会议室 | 全部（跨角色协作场） | 一切（顺手沉淀） | 讨论、拉人、沉淀产物 |

- 角色收敛体现在**默认值**上，而非硬隔离：默认只给你该看的，但基质随时可展开取用更多（原则一的"自由"由此保留）。
- 复用现有页面骨架（Dashboard/Conversations/Projects/Audit/Settings）与 DESIGN.md 组件（seg/proj-select/panel…），**不新起平行样式体系**。角色台子是这些页面的"取景框预设 + 顶部切换"，不是全新五套页面。

## 5. 方法论如何"涌现"（原则一的机制落点）

系统不定义方法论，但要让方法论**可复现、可传承、可进化**——全部由基质的副产品自然提供，无需专门模块：

1. **可复现**：一个人走过的路径 = 一串"创建了哪些 Context Item + 每个环节的 ContextRequest"。这串轨迹天然记录在基质与 trace 里。想复用，就把这串"取景框 + 常用 include 集合"存成一个**个人预设**（挂在操作者身份卡 `rail-me` / app_settings 下，见 `project_operator_inbox` 记忆），下次一键套用。
2. **可传承**：个人预设可被复制/分享给同角色的其他人——但这是"分享一个取景框预设"，**不是**"发布一套方法论产品"。轻量、可 fork。
3. **可进化**：哪种取材组合让 Agent 判断更准，由现有度量回路回答——`llm_traces`（trace 页）+ schema 驱动 Agent 的优化记录 + innate 记忆的 confidence/debt。方法论的"新陈代谢"复用已有基础设施，不新建。

> 关键：以上三点**没有一个需要"方法论"实体表**。它们是"取景框预设 + 轨迹 + 度量"三者的组合效果。这就是原则一"虚拟概念、不做管理"的技术兑现。

## 6. 数据模型（概念级，不含迁移）

> 说明：本节只给概念结构，**不给 SQL、不给迁移序号、不含实施**。遵循"迁移文件不可变、只新增"的规则将在实施阶段处理。

- **ContextItem**：逻辑视图/薄索引（见 §3.1）。物理上可能是：
  - 一张轻量索引表（`context_index`：id/project_id/source_kind/source_id/title/labels/created_at/trust/size_hint），由各来源写入时**顺带登记**（或后台投影任务补齐）；
  - 正文永远回原表/文件懒取，索引不存正文。
- **ContextRef**（引用）：让消息块/CR/任务能持久引用一条 Context Item。可复用现有 `ws_ref` 块思路，扩展为通用 `context_ref` 块（需三处同步：`mock.ts` 类型、`Block.tsx` 渲染、Rust 侧 JSON——遵循"新增 block 类型三处同步"规范）。
- **LensPreset**（取景框预设）：`{owner, role, include[], labels[], budget}`，挂 app_settings / 操作者身份卡；角色默认预设为系统种子，个人预设为用户派生。
- 现有表**不改语义**，最多加"登记到 context_index"的写钩子。

## 7. 已知缺口与开放问题

### 7.1 结构缺口

1. **部署/运维闭环最薄**：要兑现"设计→开发→部署完全在 AutoForge 内、不出软件"，`实施运维台` 目前几乎空白（仅有 dev_server/preview）。真正的部署、发布记录、运行观测是最大空洞。**本文先把它作为 L4 的一个台子占位**，具体能力另行设计。
2. **过程信息体量**：code_agent_log / trace 可能很大，全量纳入会撑爆预算。基质必须提供**摘要投影**（如日志只投影"改动摘要 + 尾部"，trace 只投影出入参要点），而非全文——`extract_report` / `truncate_keep_tail` 是现成砖块。
3. **检索质量**：FTS 关键词检索对"最准确上下文"可能不够。是否引入语义检索、以何种零依赖方式，是开放问题（倾向：可选 MCP，不进核心）。

### 7.2 需用户裁定的设计取舍（留待后续，不在本文强行拍板）

- **取景框的默认严格度**：默认"只给该看的"到什么程度？过严损害原则一的自由，过松回到"信息过载"。倾向"窄默认 + 一键展开"。
- **个人预设的分享边界**：个人方法论预设是否允许跨项目/跨人自由复制？涉及隔离与治理。
- **过程信息的默认纳入策略**：编码 Agent 执行时，是否**默认**纳入"相关会议室结论 + 上次日志"，还是必须显式 ref？倾向默认纳入"强相关且已摘要"的少量，其余显式 ref。

## 8. 与既有约束/愿景的对齐检查

- ✅ **后端独立化**：基质层、装配引擎、投影适配器**全为纯 Rust**，不引用 `tauri::*`；事件仍只走 `event::emit(AppEvent)`。
- ✅ **零外部依赖**：检索用 SQLite FTS，不引入 Redis/向量库/ES。
- ✅ **安全**：external_untrusted 来源必过 `has_obvious_injection`；本地源码读豁免延续 `Tool::reads_local_source()` 现有逻辑；工作区写入仍限 `.autoforge/{docs,specs,deliverables}`。
- ✅ **MCP**：MCP 结果作为 `mcp_result` 类型 Context Item 纳入基质，天然带 external_untrusted 信任级——与"MCP 结果视为不可信外部输入"约束一致。
- ✅ **设计系统**：L4 角色台子复用 DESIGN.md 既有 token 与组件，取景框切换用 `seg`，下拉用 `proj-select`，不新起样式。
- ✅ **迁移规则**：新增走"只加不改"；现有表不改语义。
- ⚠️ **需注意**：装配引擎重构 `load_project_context_for_conversation` 时必须保证**默认预设行为向后兼容**，避免会议室/编码上下文回归。

## 9. 小结

- **不做**：方法论实体、方法论管理台、固化的唯一流水线。
- **做**：把"一切物料 + 一切过程信息"投影为统一的 **Context Item 基质**（L2），提供**可配置的上下文装配引擎**（L3），在上面架**角色收敛的取景框界面**（L4）。
- **结果**：每个人在自己收敛的台子里，用自己习惯的路径造物料、取上下文，把最准确的上下文喂给 Agent；方法论作为"取景框预设 + 轨迹 + 度量"的组合效果**自然涌现**，无需被设计。

> 这条设计恰好是 AutoForge 对通用编码 Agent 的**结构性错位**：编码 Agent 是"按 token 租来的强 IC"，AutoForge 是"让组织的物料与上下文复利累积、并按角色分发"的工程组织操作系统。模型越强，本设计受益越大。
